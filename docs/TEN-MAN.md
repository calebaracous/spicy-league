# 10-man pickup matches

A standalone, one-off 5v5 flow that lives beside the season system and shares
nothing with it at the data level: signup → captain vote → snake draft →
ready/lobby → result. Lives under `/10-man`.

The original design handoff (screens, copy, prototype, engineering plan) is
in `docs/design/10-man/`. Treat it as the *spec that was built from*, not as
the current state — this file is the source of truth for what shipped.

## Lifecycle

```
signups ──(10th join)──▶ voting ──(10th voter)──▶ drafting ──(8th pick)──▶ ready ──(admin report)──▶ complete
   │                       │                        │                        │
   └───────────────────────┴──── cancel10Man (admin) ────────────────────────┴──▶ cancelled
```

Enum `ten_man_state` in `src/db/schema/ten-mans.ts`. Every transition except
cancel and report is a **side effect** of the action that fills the phase.
There is no admin "advance" button:

| Transition | Triggered by | Where |
|---|---|---|
| (none) → `signups` | `start10Man()` — admin | `src/app/10-man/actions.ts` |
| `signups → voting` | `joinSignup` inserting signup #10 (stamps `signupsClosedAt`) | same |
| `voting → drafting` | `castVote` when unique voters reach 10 → `electCaptains()` (stamps `draftStartedAt`) | same + `src/lib/ten-man.ts` |
| `drafting → ready` | `submitPick` inserting pick #8 (stamps `readyAt`) | same |
| `ready → complete` | `reportResult` — admin (stamps `completedAt`, `winnerCaptainUserId`, optional `durationLabel`) | same |
| any non-complete → `cancelled` | `cancel10Man` — admin | same |

**One active 10-man at a time** is enforced by a hand-written partial unique
index at the bottom of `drizzle/0000_baseline.sql`:
`ten_mans_active_uniq ON ten_mans ((1)) WHERE state NOT IN ('complete','cancelled')`.
It is *not* in the Drizzle schema (the DSL can't express it), so
`db:generate` won't know about it. A second `start10Man()` while one is
active returns `{ error: "A 10-man is already running…" }`.

## Data model

Five tables, all in `src/db/schema/ten-mans.ts`, all cascade from `ten_mans`:

- `ten_mans` — the session row. `createdBy` and `winnerCaptainUserId`
  are nullable, `ON DELETE SET NULL`. `lobbyCode`
  is generated by `start10Man`
  as `SPCY-XXXX` (random base-36). `winnerCaptainUserId` + `durationLabel`
  are the result.
- `ten_man_signups` — unique `(tenManId, userId)` and `(tenManId, signupOrder)`.
  `signupOrder` is 1..10 and is compacted when someone leaves.
- `ten_man_votes` — two rows per voter. Unique `(tenManId, voter, candidate)`.
- `ten_man_captains` — exactly two rows once elected; `captainOrder` 1|2,
  `voteCount` frozen at election time. Unique on `(tenManId, captainOrder)`.
- `ten_man_picks` — unique `(tenManId, pickNumber)` and `(tenManId, pickedUserId)`.
  Captain/picked user FKs cascade, matching season `draft_picks`.

No role/map prefs are stored (`rolePrefs` in the snapshot is always `null`).
LoL-only by product decision; there's no game column.

## Actions and guards

All in `src/app/10-man/actions.ts`. Unlike the season actions, these
**return `{ error }`** on expected failures instead of redirecting (they're
called from client components, not from `<form action>`). Inside an action
body, throw `TenManError("user-facing message")`; the `run()` wrapper turns
it into `{ error }`. Don't let plain `Error`s escape for expected cases: a
thrown server-action error crashes the board into `src/app/error.tsx` and
its message is stripped in production. Auth guards still redirect. On the
client, call actions through `useTenManAction()` (`_phases/shared.tsx`),
which runs them in a transition and renders the error with `<ActionError>`.
Every
state-changing action except `start10Man`/`cancel10Man`/`reportResult` runs
inside `db.transaction()` and takes `SELECT … FOR UPDATE` on the `ten_mans`
row first — this is what serialises the "10th signup" and "10th voter" races.
It's also why `src/db/client.ts` uses the Neon **Pool** (WebSocket) driver
rather than HTTP: the HTTP driver can't do interactive transactions.

| Action | Who | Checks |
|---|---|---|
| `start10Man()` | `requireAdmin` | DB partial unique index |
| `cancel10Man(id)` | `requireAdmin` | state ≠ `complete` |
| `joinSignup(id)` | `requireAuth` | state = `signups`, count < 10 (`signups-full`), idempotent if already in |
| `leaveSignup(id)` | `requireAuth` | state = `signups`; re-numbers remaining `signupOrder` |
| `castVote(id, [a, b])` | `requireAuth` | a ≠ b, state = `voting`, caller **and both candidates** are signups. Self-votes allowed (volunteering to captain). Delete-then-insert, so re-voting replaces. |
| `submitPick(id, userId, expectedPickNumber)` | `requireAuth` | state = `drafting`, < 8 picks, `expectedPickNumber` is the next pick (the board sends `picks.length + 1`, so a late click is rejected instead of credited to the next captain), caller is on-the-clock captain **or admin**, picked user is a signup and isn't a captain or already picked |
| `reportResult(id, {winnerCaptainUserId, durationLabel?})` | `requireAdmin` | state = `ready`, winner is one of the two captains |

Note: guards use `requireAuth`, not `requireOnboarded` — username isn't
needed for anything here.

Every action that changes state calls `revalidatePath("/10-man")` and
`/10-man/{id}`; SSE handles the live push.

## Captain election

`electCaptains(tx, tenManId, votes)` in `src/lib/ten-man.ts`: tally votes,
sort by count desc with a `Math.random()` comparator for ties, take top 2,
insert as captain 1 and 2. Only candidates who received ≥ 1 vote are
considered. Runs inside the `castVote` transaction.

## Draft order

Fixed 8-pick snake for 2 captains: `PICK_ORDER_C1_C2 = [1, 2, 2, 1, 1, 2, 2, 1]`
in `src/lib/ten-man.ts`. Duplicated (for the client) as `SNAKE_ORDER` in
`src/components/ui/snake-order-strip.tsx` — change both together. This is
independent of the season draft's `captainOrderForPick`.

`onTheClock` is derived in `getTenManSnapshot` from `picks.length`, never stored.

## Realtime

Identical pattern to the season draft (see [DRAFT.md](DRAFT.md)):
`src/app/api/ten-man/[id]/stream/route.ts` polls `getTenManSnapshot(id)`
every 2s, compares the `JSON.stringify`'d snapshot with the last one, emits
`update` on change and `: ping` otherwise. `maxDuration = 300`. (It used to
hash counts only, which missed a player changing their vote — `castVote`
deletes and re-inserts, so `votes.length` doesn't change.)

Client: `src/app/10-man/[id]/live-board.tsx` opens the `EventSource` and
switches on `snap.tenMan.state` to render one phase board from
`src/app/10-man/[id]/_phases/`:

| State | Board |
|---|---|
| `signups` | `signup-board.tsx` (join/leave, admin cancel with confirm; signed-out viewers get a "Sign in to join" link back to the board) |
| `cancelled` | `cancelled-board.tsx` (terminal banner + link back to `/10-man`) |
| `voting` | `voting-board.tsx` (pick 2; auto-submits on second tap, reverts on error) |
| `drafting` | `draft-board.tsx` (pool + `SnakeOrderStrip`; admins can pick at any time on behalf of the on-the-clock captain — the "Admin — picking for {captain}" pill names who) |
| `ready` | `ready-board.tsx` (rosters, lobby code + copy, admin report-result form; exports `TeamRoster`) |
| `complete` | `complete-board.tsx` (winner banner; admin "start another" → `start10Man`) |

`_phases/types.ts` holds the client-serialisable `TenManSnapshotClient`
(dates may arrive as strings). `_phases/shared.tsx` has `Avatar`,
`PhaseBanner` (its title is the board's `<h1>`), `useTenManAction` and
`ActionError`. Board grids stack on phones and go side-by-side at `md`.

## Pages

- `/10-man` (`src/app/10-man/page.tsx`) — if a 10-man is active, **redirects**
  to `/10-man/{id}`. Otherwise renders `_landing.tsx`: 4-step explainer,
  admin "Start a 10-man" button, last 10 completed results
  (`getRecentTenMans`).
- `/10-man/[id]` — server-fetches the snapshot, passes it to the live board.
  404 if the id doesn't exist. Cancelled and completed sessions stay viewable.

## Site chrome integration

- Nav link `10-man` in `src/components/site-header-client.tsx`.
- Live pill in `src/components/site-header.tsx`: a live **season** wins; if
  none, an active 10-man shows `10-MAN · n/10`, `· VOTING`, `· DRAFTING`, or
  `· READY` linking to the session.

## Where to look when…

- …"Start" fails → an active 10-man already exists (partial unique index). Cancel it first.
- …the lobby is stuck in `voting` → fewer than 10 distinct voters. Check `ten_man_votes`.
- …captains look random → they were tied; the tie-break is `Math.random()`.
- …a pick is rejected → the board shows the `TenManError` message inline
  (`<ActionError>`). A generic "Something went wrong" means a non-`TenManError`
  escaped — check the server log.
- …deleting a user fails → check `0001_reconcile_live_schema` has been
  applied; before it, `ten_man_picks` and `ten_mans` FKs blocked user
  deletion. See [DATA-MODEL.md](DATA-MODEL.md) → Migrations.
